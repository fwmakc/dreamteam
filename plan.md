# Dreamteam как глобальный CLI: план переделки

> Статус: согласовано в диалоге, работа не начата.
> Репозиторий остаётся мастерской: в нём разработка и пробы, из него публикуется пакет.

## Цель

`npm i -g` → команда `dreamteam` запускается в **любой папке проекта** (как
opencode). Приложение создаёт там служебную папку `.dreamteam/` и живёт тремя
слоями: код пакета (read-only), пользовательский дом, проект.

## Слои — итоговая карта

| Слой | Путь | Что лежит |
|---|---|---|
| Пакет | `node_modules/…/dreamteam` | код, встроенные тула (`src/tools/*`), wizard; перезаписывается только обновлением пакета |
| Дом пользователя | `~/.dreamteam/` | `providers.json` (ключи!), `settings.json`, `sessions/`, `transcripts/` — личное, одно на все проекты |
| Проект | `<cwd>/.dreamteam/` | `agents.json`, `manager.json`, `projects.json`, `tools/`, `memory.json` — команда этого проекта |

Ключевые следствия:

- **Граница безопасности становится физической**: встроенные тула и их дефолтные
  политики (deny за папкой, маски, секреты) живут в пакете; `.dreamteam/tools/`
  — пользовательская полка, скачанный файл не может подменить `shell.ts`;
  проверка «встроенные имена занять нельзя» остаётся вторым рубежом.
- **Проект = cwd**: папка проекта больше не поле в `projects.json` — вы уже в
  ней. `projects.json` перечисляет только серверы (hosts) проекта. Псевдо-проект
  `dreamteam` и общая `workspace/` исчезают; рабочая папка действия по умолчанию —
  текущая.
- **Сессии — в доме** (личная история переписок, договорились), **память — в
  проекте** (`memory.json` — состояние команды: лог итогов, otherChats, shared;
  контекст проектов не должен смешиваться; можно коммитить или гигнорить —
  выбор строкой в `.gitignore`).
- **Секреты и git**: в `.dreamteam/projects.json` бывают пароли хостов. При
  первом запуске в проекте с git: если `.dreamteam/` не в `.gitignore` —
  предупреждение с готовой строкой для копирования. В README — то же самое.

## Принятые решения (все обсуждением закрыты)

1. Wizard: первый запуск без `~/.dreamteam/providers.json` — один экран
   настроек (тип провайдера, ключ), запись файла, дальше сразу живой менеджер.
2. Отсутствующий конфиг — не падение, а скаффолдинг+разговор; **битый** конфиг —
   как раньше, fail-fast с внятной ошибкой.
3. Новый чат **всегда начинается с менеджера**: он консьерж — справка по
   командам, статус проектов, позвать/добавить агентов, включить тула.
4. Менеджер и модератор **не сливаем**: разные работы. В чате «только менеджер»
   планирование вырождается (отвечает он сам), после `chat.add` снова работает
   модератор.
5. Менеджер может **включать** тула и править карточки (это конфиг, есть
   валидация и откат), но **не пишет код тулов** в `.dreamteam/tools/*.ts` —
   максимум каркас-заготовку с живым подтверждением. LLM не расширяет себе
   полномочия.
6. `tsx` остаётся зависимостью пакета — пользовательские тула остаются `.ts`
   без шага сборки.
7. Миграция текущих данных — однократная, вручную по инструкции из README
   (или скриптом `dreamteam migrate`): `data/sessions`, `data/transcripts`,
   `config/providers.json` → `~/.dreamteam`; `data/memory.json` →
   `<проект>/.dreamteam/memory.json`.

## Фазы

### Фаза 0 — слой путей (фундамент) — ВЫПОЛНЕНА

Сейчас всё резолвится от корня приложения (`src/index.ts:70-77`: `ROOT`,
`CONFIG_DIR`, `DATA_DIR`, `MEMORY_FILE`; `src/settings.ts:73`; загрузки в
`loadToolsConfig`/`loadProjects` принимают `root`). Ввести три явных корня:

- `APP_ROOT` — папка пакета (для встроенных тулов; configs пакета больше не
  читаются из него);
- `DT_HOME` — `~/.dreamteam` (переопределяется переменной окружения `DT_HOME`
  для проб);
- `DT_PROJECT` — `<cwd>/.dreamteam`.

Работа:

- Новый модуль `src/paths.ts`: единственное место, где считаются пути; в
  index.ts остаётся только импорт.
- Разнести чтения: providers+settings ← дом; agents/manager/projects/memory ←
  проект; sessions/transcripts ← дом; `loadUserTools` ← `<DT_PROJECT>/tools`.
- `workspaceFor()`: проект (префикс блока) → его `dirAbs`… — упрощение: без
  `dir` рабочая папка = cwd; префикс проекта в блоках теперь адресует только
  серверы/настройки, локально всё идёт в cwd. Поля `dir` в `projects.json`
  больше нет (валидация: только hosts).
- Пробники переводятся на `DT_HOME` во временных каталогах (сейчас они и так
  на tmp — подстроить вызовы).

Сделано: `src/paths.ts` (APP_ROOT / DT_HOME / DT_PROJECT / WORKSPACE +
`migrateLegacy()` с env-предохранителем — при заданных DT_HOME/DT_PROJECT
миграция молча не работает, пробники никогда не трогают реальные данные);
`dir` в projects.json и `workspace` в settings.json удалены (fail-fast с
внятной ошибкой); рабочая папка инструментов — всегда cwd; префикс проекта
адресует только серверы. Сверх плана: служебная папка `.dreamteam` запрещена
тулам на чтение и запись (pathScan, files, scp put/get) — иначе агент мог бы
править собственные конфиги. Пробники герметичны: TUI/стартовые гоняются
в tmp-доме и tmp-проекте с mock-провайдерами. Этот репозиторий переведён:
`config/` → `.dreamteam` (agents/manager/projects) + `~/.dreamteam`
(providers/settings/user), `data/` → `~/.dreamteam` (sessions/transcripts),
`tools/` → `.dreamteam/tools`; предохранительная копия — `migration-backup/`.

Проверка: tsc, `npm run probe`, `probe:e2e`, `probe:tui` (изоляция данных),
md5-контроль. Коммит «слой путей».

### Фаза 1 — wizard и скаффолдинг — ВЫПОЛНЕНА

Мастер (`src/wizard.ts`) идёт до TUI, в обычном терминале: тип провайдера
(openai-совместимый / anthropic / gigachat / mock), baseUrl и модель, ключ.
Ключ вводится вслепую (sudo-стиль: на время секрета весь вывод readline уходит
в карман — перерисовки readline случаются и после резолва вопроса), хранится
в `~/.dreamteam/.env` как `DREAMTEAM_API_KEY` и подмешивается в `process.env`
сразу — без перезапуска. anthropic/gigachat требуют ключ (пустой ввод —
повтор вопроса), у локального openai-совместимого он опционален.

Скаффолдинг не молча: `settings.json` с дефолтами; в проекте — `.dreamteam`
(пустая команда, менеджер на дефолтном провайдере, пустые серверы, `tools/`),
каждый созданный файл — заметка в стартовом выводе. При git-проекте без
`.gitignore`-строки — предупреждение с готовой строкой, один раз, при создании.
Не-TTY без провайдеров — честный отказ («первый запуск проходит мастер: запусти
приложение в терминале»), не тихий mock. Битый конфиг мастером не лечится —
упадёт позже с внятной ошибкой, как раньше. Проба `tests/probe-wizard.ts`
(34 проверки: все ветки мастера, изоляция слоёв, отказ не-TTY, gitignore)
вошла в `npm run probe`; смоук в псевдотерминале: мастер → mock → чат → /exit.

- Коммит «wizard + скаффолдинг».

### Фаза 2 — менеджер-консьерж

- Новый чат стартует с участником-менеджером (правило); пока он единственный —
  все реплики адресуются ему, `planTurns` не вызывается.
- Приветствие нового разговора: короткое, живое, от менеджера.
- Блок состояния `MANAGER_PROMPT` пополняется: статус проектов (hosts, кто
  назначен), включённые тула каждого агента, список slash-команд (генерится из
  того же источника, что `/help` — не разъедется).
- Новые действия протокола (белые списки, tmp+rename, валидация `loadTeam`/
  `loadProjects` после записи, откат при ошибке — как у `team.add`):
  - `tool.grant` `{agent, tool, card}` — включить тул агенту / править карточку;
  - `project.add` `{id, hosts?}`, `project.host.add` `{project, name, host…}`.
- Забор: менеджер не пишет файлы в `tools/` (действие отсутствует в протоколе
  физически).
- `probe-manager`: новые действия, откат, отказ писать в tools/.
- Коммит «менеджер-консьерж».

  **— ВЫПОЛНЕНА.** Сделано: новый разговор (`/new` и самый первый) стартует
  один на один с менеджером — `participants=['manager']`, все реплики без
  @-упоминаний уходят ему, модератор и `planTurns` не запускаются; при выходе
  последнего участника менеджер остаётся в чате. `/new` зовёт менеджера с
  просьбой поприветствовать (mock-ветка в `providers/mock.ts` по «Поприветствуй»).
  Стейт менеджера дополнен: тула каждого агента, реестр проектов (серверы,
  кто назначен), список slash-команд — генерится из `COMMANDS` в
  `src/completion.ts`, того же источника, что `/help`. Новые действия протокола
  `tool.grant` / `project.add` / `project.host.add` — белые списки полей,
  запись tmp→валидация (`loadTeam`/`loadProjects`)→rename с откатом; в `tools/`
  менеджер писать не может физически (такого действия нет). `loadTeam` больше
  не считает пустую команду ошибкой — `[]` из скаффолда теперь легитимный старт
  консьержа (баннер подсказывает «один на один с менеджером»). `probe-manager`
  расширен (парсер новых действий, стейт, grantTool, проекты с сохранением
  чужих полей, откат); смоук в псевдотерминале: пустой проект → первая реплика
  менеджеру → `team.add` исполнен → `/new` с приветствием → `/exit`.

  `dreamteam-cli`, если `dreamteam` на npm занят — проверить перед паблишем.
- `npm link` — локальная проверка глобальной установки на реальных проектах

- README: установка, первый запуск, wizard, слои, менеджер-онбординг, миграция;
  дерево структуры — новое.
- Коммит «упаковка» (+ `npm publish`, когда скажете).

  **— ВЫПОЛНЕНА.** Сделано: `dreamteam` на npm свободен — имя пакета оставлено;
  `bin/dreamteam.js` — обёртка «зарегистрировать tsx-загрузчик → импорт
  `src/index.ts`», `package.json`: bin/files (bin, src, docker, README), tsx
  переехал в dependencies, `"private"` снят; `npm pack` — 40 файлов, 142 КБ,
  без мусора. `npm link` проверен в песочнице смоуком в псевдотерминале:
  глобальная команда `dreamteam` в пустой папке → мастер (mock) → оба слоя
  созданы → приветствие менеджера → `/exit`. Для этого дополнено ядро: менеджер
  теперь здоровается и при старте пустого разговора (не только по `/new`),
  только в TTY; mock-менеджер научен demo `chat.add` («позови Теста в чат»)
  и team.add сразу с тулами files+shell; `probe-tui` переписан под консьерж-
  поток (21 проверка: приветствие на старте, всплывашка с менеджером, team.add
  первой репликой, chat.add, раунд с инструментами, повторное обращение).
  README переписан под слои: установка/мастер/онбординг/миграция (автоперенос
  `config/`+`data/` при старте — он уже был в `paths.ts`), новое дерево,
  команды и пути (`~/.dreamteam`, `<проект>/.dreamteam`, рабочая папка = cwd).

### Фаза 4 — миграция и уборка

- `dreamteam migrate` (или инструкция): перенос данных из старой папки
  приложения в новые слои; старая `data/` не удаляется — архив.
- Прогон всего набора проб на новой схеме; isolation-процедура для `probe:tui`
  обновлённая (tmp-дом).
- Финальный коммит и пуш.

  **— ВЫПОЛНЕНА.** Сделано: перенос уже был автоматическим (`migrateLegacy` в
  `paths.ts`, вызов на старте `index.ts` с заметками «миграция: …»), и вживую
  он уже отработал — старых `config/` и `data/` в репозитории больше нет,
  всё в слоях. Отдельная команда не понадобилась. `tests/probe-migrate.ts`
  (17 проверок): переезд всех файлов по слоям, rename-источники, каталоги
  остаются архивом, повторный вызов ничего не перезаписывает и не выдаёт
  лишних заметок, защиты `DT_HOME`/`DT_PROJECT` и «нет старых каталогов».
  Зонд поймал дефект — пустые каталоги-архивы `data/sessions`/`transcripts`
  печатали заметку о переносе на каждом старте — исправлено (заметка только
  о реально перенесённых файлах). `probe-migrate` включён в `npm run probe`;
  обновлены README («Проверки») и шапка `probe-tui` (консьерж-сценарий).
  Полный прогон на новой схеме: tsc чисто, `probe` 463, `probe:e2e` 28,
  `probe:tui` 21, оба смоука (консьерж и глобальная установка) — зелёные.
  Публикация на npm — по команде.

### Фаза 5 — ядро как API и графическая оболочка — ВЫПОЛНЕНА

Цель: текущий код консольного приложения становится ядром (движком), к которому
подключаются оболочки. Терминальный TUI — первая из них, локальный веб-GUI —
вторая. Никакой магии: явный интерфейс событий, честный human-in-the-loop.

- **Этап 1 — разрез ядро/оболочка — ВЫПОЛНЕНА.** Сделано: вся бизнес-логика
  (раунды, менеджер, исполнение действий, цикл тулов, память, команды)
  переехала в `src/core/engine.ts`, единственный канал к оболочке — интерфейс
  `Presenter` (`src/core/presenter.ts`); в ядре ни одного `console.log`.
  `CliPresenter` воспроизводит прежнее поведение терминала один в один
  (стрим, спиннер, вопрос y/n через очередь ввода, выбор разговора),
  поведение TUI не изменилось — все пробы зелёные (26950e1).
- **Этап 2 — API-сервер — ВЫПОЛНЕНА.** Сделано: `dreamteam serve` — локальный
  HTTP+WS на 127.0.0.1 (`ws`, порт `DT_PORT`/8787), `ServerPresenter` шлёт
  JSON-события (state/notice/error/turn_header/busy/delta/turn_end/say/
  tool_results/attachment/confirm/choose_session/session_opened), клиент
  отвечает hello/user_message/abort/confirm_response/choose_response/rpc
  (state, sessions.list, session.open/new/delete, chat.add/remove,
  provider.set). Общий старт оболочек — `src/core/bootstrap.ts`. Вопрос без
  ответа — отказ по таймауту (5 минут), без клиентов — сразу отказ. Проба
  `tests/probe-api.ts`: статика, WS-сценарий консьержа, все rpc, вопросы
  (ec48b26; герметичность probe:api дополнена chdir в tmp — 720a2c0).
- **Этап 3 — веб-GUI — ВЫПОЛНЕНА.** Сделано: `gui/` (index.html, app.js,
  style.css — vanilla, без сборки), сервер раздаёт статику с защитой от
  выхода за каталог: панель разговоров (открыть/новый/удалить с
  подтверждением), команда с составом чата (клик — позвать/вывести),
  провайдеры (клик — основной), чат со стримом и результатами тулов,
  кнопки ✓/✗ для вопросов инструмента, «⏹ Прервать». Проверено живым
  браузером на mock-сервере во временных папках; по пути исправлены
  залипание статус-бара после раунда и несвежий state после
  session.open/delete (broadcastState в serve.ts), плюс `npm run serve`
  теперь действительно стартует сервер.
- Коммит+пуш после каждого этапа; публикация — по команде.

## Дисциплина (без изменений на всех фазах)

- Правки конфигов пользователя — только явным заказом; `data/` не трогаем,
  перед пробами с записью — изоляция и md5-контроль после.
- Fail-fast для битых конфигов, внятные ошибки, явное лучше неявного.
- Коммит+пуш после каждой фазы (тематические коммиты).
- `workspace/PLAN.md` пользователя не трогаем — этот план лежит в `plan.md`
  корня репозитория.
